# 저작 에이전트 전 건 판정(`reviewed`) — 현재 상태와 문제

작성 2026-08-17 · 대상 브랜치 `feat/저작-에이전트가-전-건-판정을-내고-미커버를-먼저-제안한다-ARTEL-404` ([PR #85](https://github.com/project-artel/artel-agent-server/pull/85))

다른 세션에서 이 주제를 이어 논의하기 위한 인계 문서. 실험 결과 전문이 아니라
**지금 무엇이 있고 무엇이 문제인지**만 담는다.

---

## 1. 무엇을 만들었나

시나리오 저작 에이전트가 시나리오를 쓰기 전에 **프로젝트의 모든 TestCase를 이 요청에
포함(in)/제외(out)로 판정**하고, 그 판정을 산출물에 함께 싣게 했다.

- 프롬프트: `app/prompts/scenario/v5/system.md` (v4에서 분기)
  - 0번 단계 — "스텝을 쓰기 전에 목록의 **모든 id**를 in 또는 out에 정확히 한 번씩 넣어라"
  - sibling 경고 문단 — 씬·스텝 문구가 같고 `precondition`만 다른 케이스는 한 세트다
  - 자기 검사 문단 — `in`에 넣은 id가 전부 어떤 스텝의 `case_id`로 실렸는지 확인해라
- 스키마: `app/agents/scenario/schemas.py`의 `ReviewedCases` (`in`/`out` 두 배열),
  `ScenarioAgentResult.reviewed`
- 전달: `app/api/sessions.py`의 `_result_event` — `None`이 아니면 result 이벤트에 실어 보냄

**설계 의도**: "안 본 케이스"와 "보고 버린 케이스"를 구분할 수 있게 만드는 것. 판정이 없는
id를 집합 뺄셈으로 찾을 수 있으면, 모델에게 "다 읽었니?"라고 묻는 순환을 피할 수 있다.
세는 일은 의도적으로 **와이어 반대편(오케스트레이션)** 몫으로 남겼다.

## 2. 어떻게 채워지고 어디까지 가나

한 번에 만들어진다. 케이스마다 도구를 부르거나 파이썬 쪽에 누적하는 경로는 없다.

```
턴 시작
 └ 에이전트 루프 (LangChain create_agent)
    └ 마지막 턴: ToolStrategy 구조화 출력 도구 1회 호출
         arguments = { message, scenarios, reviewed: { in:[...], out:[...] } }
                                            ↑ 배열이 존재하게 되는 유일한 순간
 └ 코드 레이어: structured_response → ScenarioAgentResult 파싱
 └ WebSocket result 이벤트 → 오케스트레이션 서버
```

케이스 목록 전량은 시스템 프롬프트에 들어 있다(ARTEL-319). 모델은 컨텍스트를 보고
id를 나열해 쓴다. 그 사이에 값을 만들거나 고치는 코드는 없다.

**`reviewed`를 읽는 코드는 `sessions.py`의 3줄이 전부다.** 이 레포에 검사는 없다.

---

## 3. 문제

### 3-1. `reviewed = None`이 두 가지를 겸한다 — 가장 시급

지금 `None`의 의미는 "판정할 모집단이 없었다(= `test_case_list`가 비었다) → 검사 건너뛴다"이고,
이것이 **롤백 경로**로도 쓰인다. 그런데 실측에서 **모델이 그냥 `reviewed`를 안 내는 경우가
있다**. 둘이 같은 값이라 구분되지 않는다.

결과적으로 모델이 판정을 포기한 턴이 "검사할 게 없는 턴"으로 읽혀 **조용히 통과**한다.

→ `test_case_list`가 비어 있지 않은데 `reviewed`가 없으면 실패로 기록되어야 한다.
   이건 이 레포에서 지금 할 수 있는 일이다.

### 3-2. 목록이 1000건이면 판정 배열이 무너진다

실측(각 10런):

| 목록 크기 | 전 건 판정에 성공한 런 | 실패 양상 |
|---|---|---|
| 100 · 250 · 500 | 9~10 / 10 | — |
| **1000** | **0~2 / 10** | `out: []` 로 비움, 또는 `reviewed` 자체를 생략 |

`schemas.py` 주석의 "1000건이면 3,005토큰" 계산은 모델이 그걸 실제로 뱉는다는 전제였는데,
뱉지 않는다. 배열이 겨냥한 규모에서 배열이 안 나온다.

### 3-3. 세는 쪽이 아직 없다

`in | out == 프로젝트 전체`인지, `in`의 모든 id가 스텝의 `case_id`로 실렸는지 세는 코드가
어디에도 없다. 실측에서 실제로 잡혔어야 할 것들:

- 목록에 없는 id를 지어내 `out`에 채운 런 (id가 비어 있는 번호 구간을 그대로 메움)
- `in`에 넣고 스텝으로 안 실은 id (런당 1~3건)

전부 밖에서 셀 수 있는 종류인데, 아무도 안 세므로 지금은 통과한다.

### 3-4. 개선분의 출처를 못 가른다

v5는 판정 배열만 추가된 게 아니다. **sibling 경고 문단과 자기 검사 문단도 같이 들어왔다.**
그래서 v4 대비 개선이 관측돼도 그것이 배열 때문인지 경고 문단 때문인지 알 수 없다.

→ ablation 필요: v5에서 배열만 빼고 문단은 남긴 arm.

## 4. 실측 요약 (판단 근거)

모델 `openai/gpt-5.6-luna`, 200런(v4 100 / v5 100). 정답은 실제 DB의 `맵 화면` 28건이고,
누락은 "정답 28건 중 어떤 스텝의 `case_id`로도 안 실린 건"을 집합 뺄셈으로만 셌다.

| | 누락 발생 런 | 잃은 케이스 총합 | 최악 |
|---|---|---|---|
| v4 (판정 없음) | 5 / 100 | 51건 | 20건 |
| v5 (전 건 판정) | 1 / 100 | 2건 | 2건 |

Fisher 정확검정 **p = 0.21 — 유의하지 않다.** 심각도 차이(51건 vs 2건)가 실질적 근거이고,
통계적 근거는 아직 부족하다.

**누락을 부르는 것은 목록의 양이 아니었다.** 경쟁 씬을 넣고도 500·1000건에서는 양쪽 다
10/10 완벽했다. 실패는 목록 안에 **같은 게임을 두 벌로 적어 둔 카탈로그**가 있을 때 났다
(project 1 `맵 화면` 28건 ↔ project 3 `Map_scene` 21건처럼 의미가 겹치는 씬들).

실패할 때의 모양은 매번 같다 — 경쟁 씬은 21/21 전부 집고, 한글 씬의 **형제군을 군 단위로**
버린다(`[15~19]`, `[24,26]`, `[25,27]`, `[28,30]`, `[29,31]`). 프롬프트의 sibling 경고가
겨냥한 자리가 맞았고, 다만 발동 조건은 "케이스가 많을 때"가 아니라 "중복 카탈로그일 때"다.

*(주: 중복 카탈로그가 원인이라는 것은 데이터와 모순 없는 해석이지 직접 검증된 결론은
아니다. 확인하려면 project 3 전체를 각 크기에 넣고 다시 돌려야 한다.)*

## 5. 논의가 필요한 지점

1. `reviewed = None`의 의미 분리 — 지금 이 레포에서 고칠 수 있는 유일한 항목
2. 검사를 오케스트레이션에 붙일 것인가, 붙인다면 무엇을 셀 것인가
   (전 건 판정 / 목록 밖 id / `in` 약속 불이행 — 셋 다 지금 이벤트에 실려 나간다)
3. 1000건에서 배열이 안 나오는 것을 감수할 것인가, 다른 방식으로 바꿀 것인가
4. ablation으로 배열과 sibling 경고의 기여를 가를 것인가
5. 비용 — 판정은 매 턴 출력 토큰으로 나간다. 500건 목록이면 `out`만 450여 개 id다.
   실측상 500건 이하에서는 누락 자체가 발생하지 않았으므로, 그 구간에서는 순수 비용이다.

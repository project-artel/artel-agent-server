# ADR 0003 — 검색 key 로 본문이 아니라 그 본문을 찾을 질문을 embedding 한다

- 상태: 확정
- 근거: `app/agents/knowledge_query/schemas.py`, `app/agents/knowledge_query/agent.py`,
  `app/api/knowledge_queries.py`, `app/llm/embedding_model.py`,
  artel-orchestration-server 의 `V18__create_knowledge_embedding.sql`,
  Notion 「QA Agent 임베딩 모델 선정 근거 (ARTEL-184)」

## 결정

- knowledge 항목의 **본문을 embedding 하지 않습니다.** 항목마다 그것을 찾아낼 법한
  질문을 모델로 생성하고, 그 질문들을 embedding 해 검색 key 로 씁니다.
- 항목당 질문은 `QUESTIONS_PER_ITEM = 3` 입니다.
- 저장은 multi-vector 입니다. `knowledge_embedding.kind` 가 `QUERY` 와 `CONTENT` 를
  받고, 지금은 `QUERY` 만 채웁니다.

## 왜

### 1. 질문과 서술문은 embedding 공간에서 안 붙습니다

- QA 엔지니어가 치는 것은 질문입니다 — 「골드 모자라면 어떻게 되나」.
- 항목은 서술문입니다 — 「구매는 소지금이 가격 이상일 때 가능하다」.
- 형태가 다르고, 그 둘은 생각보다 가깝지 않습니다.
- **질문끼리 맞추면 양쪽이 대칭이 됩니다.** 그것이 이 경로가 사는 이유의 전부입니다.

### 2. 셋인 이유는 받쳐 줄 것이 없기 때문입니다

- 이번 단계는 본문(`CONTENT`) 벡터를 만들지 않으므로 **폴백이 없습니다.**
- 생성 질문 하나가 빗나가면 그 항목은 검색으로 도달할 수 없고, 원인을 알려면
  사람이 생성물을 읽어야 합니다.
- 개수로 그 위험을 낮춘 것이 셋입니다.
- **다만 셋은 하한이 아니라 상한입니다.** 코드가 비대칭으로 다룹니다.

| 모델이 낸 개수 | 무엇이 일어나나 |
| --- | --- |
| 0 개 | 항목 하나가 실패. 아무 데도 색인되지 않은 항목은 검색으로 못 찾고, 저장하는 쪽이 그것을 알 방법이 없음 |
| 1~3 개 | 그대로 저장 |
| 4 개 이상 | `queries[:3]` 으로 잘라냄. 남는 질문도 유효한 key 라 개수 때문에 항목을 버리는 것이 더 비쌈 |

### 3. 이 경로는 성능을 올리지 않고 조금 깎습니다

- ADR 0002 의 34/34 는 **검색어 → 본문**을 잰 값입니다.
- 실제 파이프라인은 **검색어 → 생성 질문**이므로, 생성 질문 102 개
  (34 항목 × 3) 를 다시 embedding 해 쟀습니다.
- 결과는 **top-1 32/34, MRR 0.9706** 입니다. 빗나간 둘은 모두 rank 2 였고 근접
  distractor 쌍이라 사람이 봐도 갈리는 자리였습니다.
- 즉 이 결정이 사는 것은 점수가 아니라 **대칭성**입니다. 그래도 다른 후보들의
  본문 직접 매칭보다 나쁘지 않습니다.

### 4. 항목마다 호출을 따로 겁니다

- 한 호출에 여러 항목을 실으면 N 벌의 질문을 옳은 N 개 항목에 붙여 두어야 하는데,
  **구조화 출력에 그것을 강제하는 것이 아무것도 없습니다.**
- 목록이 한 칸 밀리면 모든 항목이 조용히 **이웃의 질문으로 색인됩니다.**
- 항목마다 부르면 그 항목의 질문이 다른 것에 속할 수 없고, 실패 하나가 배치 전체가
  아니라 항목 하나로 끝납니다.
- 실제로는 `asyncio.gather` 로 배치 안에서 동시에 돕니다. `KNOWLEDGE_QUERY_BATCH_LIMIT`
  이 제한하는 것은 payload 크기가 아니라 그 fan-out 입니다.

### 5. multi-vector 로 둔 이유

- 벡터를 `knowledge` 의 컬럼으로 붙이지 않고 별도 테이블로 뺐습니다.

| 무엇 | 컬럼이면 | 별도 테이블이면 |
| --- | --- | --- |
| 항목당 질문 3 개 | 컬럼 하나로 표현 못 함 | 행 셋 |
| `CONTENT` 벡터 추가 | 마이그레이션 | 행 추가 |
| 되돌리기 | 마이그레이션 | `DELETE WHERE kind='CONTENT'` |
| 모델 교체 | 무중단 불가 | 새 `model` 값으로 행을 채워 두고 다 차면 전환 |

- 「생성 질문 방식이 본문 embedding 보다 실제로 나은가」를 나중에 나란히 놓고 잴 수
  있게 열어 둔 자리이기도 합니다.

## 거절한 대안

| 대안 | 왜 거절했나 |
| --- | --- |
| 본문을 그대로 embedding | 질문과 서술문이 embedding 공간에서 안 붙음. 완전 기각이 아니라 `kind='CONTENT'` 자리로 유보 |
| 항목당 질문 1 개 | 폴백이 없어 하나가 빗나가면 항목이 통째로 도달 불가가 됨 |
| 한 호출에 여러 항목을 배치 | 목록이 한 칸 밀리면 이웃의 질문으로 색인됨. 오류 없이 틀림 |
| 벡터를 `knowledge` 컬럼으로 | 항목당 3 개를 표현 못 하고, `CONTENT` 추가와 모델 교체가 마이그레이션이 됨 |
| 개수가 3 을 넘으면 항목을 거절 | 남는 질문도 유효한 key 라, 프롬프트가 정중히 물은 개수 때문에 항목을 버리는 것이 더 비쌈 |

## 대가

| 대가 | 무엇이 일어나나 |
| --- | --- |
| top-1 이 34/34 에서 32/34 로 내려감 | 이 경로의 비용임. 대칭성과 맞바꾼 것 |
| 항목 하나마다 모델 호출 하나 | 색인 비용이 항목 수에 비례함. 기본 `KNOWLEDGE_QUERY_BATCH_LIMIT` 은 100,000 이라 사실상 상한이 없음 |
| 실제 저장 개수가 1~3 으로 흔들림 | 「셋이라 안전하다」는 보장이 아니라 최선의 경우 |
| 생성 질문에 어휘 누출이 남음 | 측정에서 게임 내 우편함을 「최대 **이메일** 수는」이라고 물은 것이 한 건. 검색은 정상이었으나 프롬프트에서 조일 자리 |
| `kind` 는 이 저장소가 모름 | `QUERY`/`CONTENT` 는 저장하는 쪽의 개념임. 이 서버는 벡터를 만들 뿐이고, `app/` 어디에도 그 discriminator 가 없음 |
| `QUERY` 문자열이 공용 enum 이 아님 | orchestration 의 Kotlin 상수 둘과 DB `CHECK` 제약이 전부. 한쪽을 고치면 다른 쪽이 따라오지 않음 |

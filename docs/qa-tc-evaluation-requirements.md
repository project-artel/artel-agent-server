# QA 영상 기반 TC 평가와 agent 신뢰도 측정 추가

작성일: 2026-10-27 (Asia/Seoul)

이 문서는 사용자 인터뷰에서 확정한 제품 요구사항과 이후 구현 결정을 정리한다. 사용자의 개발 요청에 따라 구현과 검증을 진행 중이며, 배포 완료를 뜻하지 않는다. 인터뷰 이후 구체화한 기술 선택은 11절, step을 참고 절차로 두는 추가 결정은 12절에 기록한다.

## 1. 목표와 1차 범위 확정

최우선 목표는 사용자가 TC 검증 당시의 영상을 보고 agent 판정이 맞았는지 평가하고, 그 피드백을 다음 검증에 활용하며, 오탐률·미탐률로 agent의 신뢰도를 확인하는 것이다.

1차 구현에는 다음을 모두 포함한다.

- orch를 통한 스트리밍 중계와 QA 전체 영상의 S3 저장.
- TC 검증 시작·결과 보고 시각 기록 및 QA history·TC 화면에서 영상 재생.
- 사람의 TC 판정 평가, 선택적인 이유 작성, 평가 수정 이력 보존.
- 같은 TC의 다음 검증에 피드백 자동 제공.
- 프로젝트 전체 신뢰도 지표, 기간별 추이, TC별 상세.
- 진행 방법을 모르는 QA agent의 사용자 질문, 브라우저 알림, 답변 후 재개.
- 일반 issue와 TC 실패 issue 구분, 반복 실패 묶음, 관련 화면 링크.

TC 결과 평가를 먼저 진행한다. 영상 저장 → 검증 구간 기록·재생 → 사람의 평가 → 피드백 반영·신뢰도 집계가 의존 관계이며, 사용자 질문과 issue 묶음도 같은 1차 범위다. 구체적인 개발 일정은 정하지 않았다.

## 2. 프로젝트 멤버 접근과 수정 허용

최종 인터뷰 결정에 따라 이번 기능에 별도의 역할별 권한을 추가하지 않는다. 프로젝트 멤버 모두가 해당 프로젝트의 영상·QA history·TC 결과·평가·피드백·관련 issue를 조회하고 수정할 수 있다.

- 영상 열람은 QA history 조회와 같은 접근 범위를 사용한다.
- TC 편집자, 평가 전담자, 관리자만으로 평가 권한을 제한하지 않는다.
- 프로젝트 멤버 누구나 QA 질문에 답변할 수 있다.
- 알림 구독 여부는 알림 수신 조건이며, 답변 권한 조건이 아니다.
- 이 결정은 프로젝트 외부 사용자에게 접근을 허용한다는 뜻이 아니다.

## 3. orch 중계와 QA 전체 영상 저장 추가

기존 동작은 스트림을 브라우저에 직접 전달하고 QA 전체 영상은 저장하지 않는 방식이다.

변경할 전달 경로는 실행 환경 → orch 서버 JVM 프로세스 → 브라우저다. orch 측에서 스트림을 수신·중계하고, 저장 효율을 고려한 동영상 포맷으로 인코딩해 S3에 저장한다. 구현 코덱·컨테이너·프로토콜은 11절에 기록한다.

- TC 주변 구간만 저장하지 않고 QA 실행 전체 영상을 저장한다.
- 사용자 답변을 기다리며 QA가 일시 정지된 동안에도 화면 변화를 확인할 수 있도록 녹화를 계속한다.
- 영상은 30일 후 자동 삭제한다.
- 영상 삭제 후에도 agent 판정, 사람의 평가, 평가 수정 이력, issue 및 발생 이력은 유지한다.
- 영상 저장이 실패해도 agent가 계속 검증할 수 있으면 QA를 계속한다.
- 저장 실패와 영상 누락 구간을 사용자에게 표시한다. 영상이 없는 구간을 정상 저장된 것처럼 표시하지 않는다.

## 4. TC 검증 구간 기록과 재생 추가

QA agent는 TC 검증 시작을 tool로 명시하고, `report_test_case`로 판정 결과와 검증 종료를 명시한다. 시작 tool의 정확한 이름과 API 계약은 미정이다.

- 각 검증 시도에 검증 시작 시각과 결과 보고 시각을 기록한다.
- 기본 재생 구간은 검증 시작 10초 전부터 결과 보고 5초 후까지다.
- 같은 QA 실행에서 같은 TC를 여러 번 검증해도 각 시도를 별도로 기록한다.
- QA history와 TC 화면 모두에서 해당 시도의 판정과 당시 영상을 함께 확인한다.
- QA 실행 전체 영상과 TC별 시간 구간을 연결하는 방식으로 구성한다. 별도 TC 영상 파일을 반드시 생성해야 하는 요구사항은 아니다.
- 결과 보고 전 중단된 시도도 구분해 남긴다. 종료 시각이 없는 시도의 재생 종료점은 기술 설계 시 정한다.

결과 보고 시점의 앞 10초·뒤 5초만 보여주는 초기 대안은 채택하지 않았다. 긴 검증의 핵심 장면도 포함하도록 검증 시작·종료 구간을 사용한다.

## 5. 사람의 TC 판정 평가와 수정 이력 추가

제품이 TC를 실패한 것과 agent가 잘못 판정한 것을 구분한다. 사람의 평가로 agent의 원래 판정을 덮어쓰지 않는다.

- 사람은 실제 결과를 통과·실패·판단 불가로 평가한다.
- 평가 이유는 선택 사항이다. Agent 판정과 다른 평가를 남길 때도 이유를 강제하지 않는다.
- 이유를 남기면 다음 검증에서 agent가 참고해 판정 정확도를 개선하는 데 도움이 된다는 취지로 안내한다.
- 이유 작성만으로 실제 신뢰도 상승이 보장된다고 표현하지 않는다. 최종 UI 문구는 구현 시 작성한다.
- 여러 사람이 평가하거나 평가를 수정하면 마지막 평가를 현재 평가로 반영한다.
- 작성자, 이전 평가와 이유 등 수정 이력을 보존한다. 별도의 검토자 승인이나 합의 절차는 두지 않는다.
- 최신 평가를 신뢰도 지표 및 다음 검증 피드백에 반영한다.

검토 대상은 사용자가 직접 선택한다. 모든 결과 검토나 통과 결과의 무작위 표본 검토를 강제하지 않는다.

## 6. 다음 TC 검증에 피드백 자동 제공

평가와 이유를 해당 TC 및 검증 시도에 연결한다. 같은 TC를 다음에 검증할 때 agent의 context에 피드백을 자동으로 제공한다.

- 피드백마다 사용자의 반영 승인을 받지 않는다.
- 피드백이 반영됐다는 별도 알림이나 확인 절차를 만들지 않는다.
- 사용자가 매 실행마다 피드백을 선택하도록 요구하지 않는다.
- 평가가 수정되면 최신 유효 평가·이유를 사용하며 수정 이력은 보존한다.
- TC 내용이 수정된 후에도 이전 피드백을 제공한다. Agent가 작성 당시 TC 버전과 현재 버전이 다르다는 점을 알 수 있도록 표시한다.
- 여기서 반영은 모델 재학습이 아니라 검증 context에 참고 자료를 제공하는 방식이다.

피드백의 길이 제한, 다수 피드백의 선택·요약 방식 등은 기술 설계에서 정한다.

## 7. 오탐률·미탐률과 검토 범위 표시 추가

집계 단위는 TC의 각 검증 시도다. 같은 QA 실행에서 같은 TC를 재검증해도 마지막 결과만 남기지 않고 각 시도를 별도로 평가·집계한다.

실제 결함이 있는 상태, 즉 사람의 실제 실패 평가를 positive로 정의한다.

| Agent 판정 | 사람의 최신 평가 | 분류 |
| --- | --- | --- |
| 실패 | 실패 | 올바른 결함 탐지(TP) |
| 실패 | 통과 | 오탐(FP) |
| 통과 | 실패 | 미탐(FN) |
| 통과 | 통과 | 올바른 통과 판정(TN) |
| 판단 불가 또는 결과 보고 전 중단 | 실패 | 미탐(FN)에 포함 |
| 판단 불가 또는 결과 보고 전 중단 | 통과 또는 판단 불가 | 오탐률·미탐률 계산에서 제외 |
| 모든 상태 | 미검토 또는 판단 불가 | 오탐률·미탐률 계산에서 제외 |

인터뷰에서 확정한 예외에 따라 판단 불가·중단도 사람이 실제 실패로 확인하면 미탐으로 센다. 이 확장된 미탐 정의를 화면 설명에 명시하고, 해당 건수를 구분해 보여준다.

- 오탐률 = FP / (FP + TN). 실제 통과로 확인되고 계산 대상에 포함된 시도 중 agent가 실패로 판정한 비율이다.
- 미탐률 = FN / (TP + FN). 실제 실패로 확인된 시도 중 agent가 탐지하지 못한 비율이며, 위의 판단 불가·중단 예외를 포함한다.
- 미검토 결과를 정답 또는 정상 통과로 간주하지 않는다.
- 지표는 사용자가 선택해 검토한 결과 내 지표다. 전체 QA 결과를 대표하는 수치로 표현하지 않는다.
- 실패 판정만 검토하면 통과 판정에 숨은 미탐을 확인할 수 없다는 한계가 있다.

화면에는 오탐률·미탐률과 함께 전체 검증 시도 수, 검토 건수, 전체 대비 검토 비율, 판단 불가 건수, 선택 편향 안내를 표시한다. 각 비율의 계산 대상 건수를 구분할 수 있어야 한다.

1차 비교 범위는 프로젝트 전체 지표, 기간별 추이, TC별 상세다. Agent 버전별 비교와 단일 종합 신뢰도 점수는 이번 인터뷰에서 확정한 범위에 포함하지 않는다.

## 8. QA 질문과 브라우저 알림 추가

QA agent가 진행 방법을 모르겠다고 판단하면 사용자에게 질문을 남기고 QA 실행 전체를 일시 정지한다. 대기 중 다른 TC를 계속 검증하지 않는다.

- 해당 프로젝트에서 알림을 구독한 사용자 전체에게 브라우저 알림을 보낸다.
- 브라우저 알림 권한이 없더라도 QA 화면에서 질문과 답변 대기 상태를 확인할 수 있다.
- 프로젝트 멤버 누구나 답변할 수 있다.
- 첫 답변을 채택하고 QA 실행을 즉시 재개한다. QA 시작자의 별도 선택이나 승인은 필요 없다.
- 자동 대기 만료 시간은 두지 않는다. QA 실행이 유지되는 동안 답변을 기다리며 사용자가 직접 종료할 수 있다.
- 대기 중에도 녹화를 계속한다.
- 재개된 agent는 채택한 답변을 참고해 진행한다.

동시 답변에서 첫 답변을 원자적으로 채택하는 방법, 실행이 유지되지 못하는 장애 상황의 복구 정책은 기술 설계 항목이다.

## 9. 일반 issue와 TC 실패 issue 구분 추가

QA agent가 명시적으로 만드는 일반 issue는 TC와 관련 없는 issue다. TC 실패는 별도의 TC 실패 issue 흐름으로 처리한다.

- 같은 TC에는 열린 TC 실패 issue 하나에 반복 실패 이력을 모은다.
- 각 발생 이력은 해당 검증 시도와 연결한다.
- 같은 TC라도 실패 원인별로 자동 분리하는 방식은 이번에 선택하지 않았다.
- issue에서 TC 상세, 각 검증의 QA history, 해당 영상 구간으로 이동할 수 있도록 링크를 제공한다.
- 일반적인 해결 처리는 사람이 직접 한다. 다음 검증이 통과했다는 이유만으로 자동 해결하지 않는다.
- 사람이 해결한 뒤 같은 TC가 다시 실패하면 새 issue를 만들고 이전 issue를 연결한다.

### 9.1 미탐 발견 시 실패 이력 추가

Agent가 통과로 판정했지만 사람이 실제 실패로 평가하면 TC 실패 issue를 자동으로 처리한다. 해당 TC의 열린 issue가 있으면 이력을 추가하고, 없으면 새 issue를 생성한다. 사람이 해결한 이전 issue가 있으면 재발 규칙에 따라 연결한다.

### 9.2 오탐 평가 시 자동 종료 예외 추가

Agent의 실패 판정을 사람이 오탐으로 평가하면 해당 발생 이력에 오탐 표시를 남긴다. 이력을 삭제하지 않는다.

- issue에 유효한 실패가 남아 있으면 열린 상태를 유지한다.
- 유효한 실패가 하나도 남지 않으면 issue를 자동 종료한다.
- 이 경우는 사람이 직접 해결한다는 일반 규칙의 예외다.

### 9.3 평가 수정 시 기존 issue 재개

오탐 평가가 실제 실패로 수정되면, 그 오탐 때문에 자동 종료됐던 기존 issue를 다시 열고 평가 수정 이력을 연결한다. 이 경우에는 새 issue를 만들지 않는다.

이 규칙은 사람이 해결한 이후 새 검증에서 실패한 재발과 구분한다. 전자는 기존 평가의 정정이고, 후자는 새 발생이므로 새 issue와 이전 issue 연결을 사용한다.

## 10. 요구사항 검증 항목 정리

아래 목록은 구현 후 확인할 기준이며, 현재 테스트를 통과했다는 의미가 아니다.

- QA 전체 영상이 orch 측 처리를 거쳐 S3에 저장되고 브라우저로 스트림이 중계된다.
- 검증 시작 10초 전부터 결과 보고 5초 후까지 QA history와 TC 화면에서 재생할 수 있다.
- 반복 검증의 시도별 판정, 영상 구간, 사람의 평가가 구분된다.
- 30일 후 영상은 삭제되지만 판정·평가·issue 이력은 남는다.
- 저장 실패에도 QA가 진행되며 누락 구간과 오류를 확인할 수 있다.
- 사람의 최신 평가가 적용되고 agent 원래 판정과 평가 수정 이력은 보존된다.
- 선택적인 이유와 이전 TC 버전의 피드백이 별도 승인·알림 없이 다음 검증에 제공된다.
- 지표가 시도 단위로 계산되며 선택 편향과 검토 범위가 표시된다.
- 판단 불가·중단을 실제 실패로 평가한 경우 미탐에 포함된다.
- QA 질문 시 전체 실행은 멈추지만 녹화는 계속된다.
- 구독자 전체가 알림 대상이고 프로젝트 멤버의 첫 답변으로 실행이 재개된다.
- 자동 대기 만료 없이 직접 종료할 수 있고, 알림 권한이 없어도 질문을 볼 수 있다.
- 반복 실패·미탐·오탐·평가 수정·해결 후 재발에 각각 정해진 issue 규칙이 적용된다.
- 별도의 평가자·영상 열람자 역할 없이 프로젝트 멤버가 접근·수정할 수 있다.

## 11. 구현 설계 결정 추가

인터뷰 이후 개발 요청을 받아 아래 구현 방식을 적용했다. 제품 요구사항을 구체화한 기술 결정이며 배포 완료를 뜻하지 않는다.

- orch JVM 프로세스 안에서 WebRTC 수신·중계와 H.264 MP4 인코딩·S3 저장을 수행한다. 별도 media-worker나 FFmpeg 자식 프로세스는 사용하지 않는다. 기본 segment는 60초·최대 32 MiB이며 서버 전체 업로드 대기열은 10개·256 MiB, 재시도는 3회로 제한한다.
- `start_test_case`가 검증 시도 UUID를 만들고 `report_test_case`로 `PASSED`·`FAILED`·`INCONCLUSIVE`를 보고한다. 서버가 시작·완료 시각을 기록한다. 프레임의 서버 시각과 monotonic 시각을 연결해 영상 PTS와 저장 구간을 기록한다.
- 앞 10초·뒤 5초는 저장된 영상 경계로 제한한다. 시작 tool 없이 기록된 과거 판정은 시작 시각을 추정하지 않는다. 보고 전 중단된 시도는 `INTERRUPTED`로 남긴다. 재연결·저장 실패 구간은 누락으로 표시한다.
- 영상 보관은 각 segment 완료 시각부터 30일이다. QA가 대기 중이어도 오래된 segment부터 삭제한다. TC를 삭제해도 검증 당시 snapshot과 논리적 TC ID를 남겨 평가·issue 이력을 조회한다.
- 비율의 분모가 0이면 값을 표시하지 않는다. 기간별 집계는 검증 시작 시각의 `Asia/Seoul` 날짜를 기준으로 하며, 평가 수정 시 과거 집계도 갱신한다.
- 사람의 판단 불가 평가는 신뢰도 계산에서 제외하고 실패 발생 이력의 유효 실패 여부는 원래 agent 판정에 따른다. agent 판단 불가·중단을 사람이 실제 실패로 평가하면 실패 issue에도 포함한다.
- 오탐으로 자동 종료된 issue를 재개할 때 다른 열린 issue가 있으면 원래 issue로 발생 이력을 합치고 이전 연결을 보존한다.
- 질문과 답변은 DB에 보존한다. 첫 프로젝트 멤버의 답변만 채택하며, QA 종료 시 대기 질문을 취소한다. agent 프로세스 자체가 종료된 실행을 자동 복구하는 기능은 포함하지 않는다.
- 브라우저 알림은 로그인한 앱이 열려 있을 때 구독한 프로젝트 전체의 SSE로 전달한다. 닫힌 브라우저를 깨우는 Web Push는 포함하지 않는다. 권한이 없어도 QA 화면에서 질문에 답할 수 있다.

## 12. TC 단위 판정 적용

시나리오의 step은 참고 절차다. Agent가 각 step을 완료하거나 판정해 보고할 의무는 없다.
`report_step`과 `report_case` 대신 `start_test_case`와 `report_test_case`로 TC 검증 시도만 기록한다.
같은 TC를 다시 검증하면 새 시도로 남기며, 미검증·판단 불가를 실제 실패로 단정하지 않는다.
영상 구간, 사람 평가, issue 연결, 신뢰도 집계의 단위도 TC 검증 시도다.
